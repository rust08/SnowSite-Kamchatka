# План реализации и критерии приёмки

## Принцип ограничения объёма

Задача — закончить ядро SnowSite, не строить муниципальную систему. Статус всех шагов ниже на момент аудита: OPEN, кроме существующих тестов и самого аудита. Не считать план реализованным. Бюджет разработки мал; делить на завершённые инкременты. Если лимит агента заканчивается, оставлять работающий commit/чёткую передачу, не полупереписанный проект.

| Шаг | Задача | Минимальный результат | Приоритет |
|---|---|---|---|
| S0 | Воспроизвести, зафиксировать baseline и исправить валидацию | Контрпримеры сохранены; 39 базовых тестов сохранены; F-01–04 покрыты | P0 |
| S1 | Exact allocation для одного набора объектов | Некратные объёмы, oracle, исправленная инверсия рейтинга, статусы optimum/timeout, компактный результат | P0 |
| S2 | Search конфигураций | 2+2 из N, fixed/optional, relocation/greenfield, topK, исключения с причинами | P0 |
| S3 | Независимый API/CLI, тесты и документация | Рабочий integration example, версия схемы, сохранённая совместимость сайта, документация и handoff | P0 |
| S4 | Переносимость / скорость / каталог | Второй граф, конфиг, матрица, CSV/GeoJSON shortlist, benchmarks, независимые screening attributes | P1 |
| S5 | Реальные данные, расширение модели | Разрешённые land candidates, ограничения грузовых дорог, ёмкости и горизонты, дополнительные расходы | WAIT_DATA |

Не начинать S5, если нет внешних данных и разрешения. В рамках S2 допустимо сначала решить точный перебор небольшого каталога; integrated MILP для 1000+ вариантов — последующий этап, если нужна масштабируемость, не обязательная игрушка для демо. Обязателен рабочий топ-K на конечном наборе и честное описание покрытия. Если exact solver не устанавливается, ограниченный oracle на малых примерах + сохранённая эвристская версия лучше, чем незавершённая миграция, но P0 exact на целевом размере останется OPEN.

### Тест производительности P1

Выбрать и зафиксировать synthetic dataset: 20 источников, 30 кандидатных площадок, 2 fixed, точное количество 2 новых, K=5. Замерить время построения матрицы отдельно от solver и объём ответа; не требовать точной оценки заранее (зависит от машины и solver). Установить time limit; report evaluated/total, bounds/status. Сравнить повторный solve с кешем. При отсутствии полного поиска — provisional. Запустить тот же core на втором небольшом графе с другими IDs; никаких координат Камчатки в математике. Для большого каталога определить входные лимиты; не обещать поиск всех участков города.

## Приоритетные запросы данных вместо новой разработки

1. Подтвердить список 2 действующих и 2 планируемых объектов: местоположение (въезд + земельный контур), период, свободная вместимость, режим работы, источник и дата проверки. Отметить какие могут переноситься, какие обязательны.
2. Определить каталог потенциальных мест (не только два заранее выбранных). На практике список кандидатов после предварительной GIS/земельной проверки; разработка может использовать тестовый shortlist.
3. Получить распределение объёмов по источникам и горизонту, для анализа устойчивости — несколько отдельных событий снегопада. Не конвертировать обращения жителей напрямую в м³.
4. Проверить ограничения дорог для loaded/empty, поворотные ограничения и доступ зимой. Документировать неизвестность.
5. Если сравниваем количество/перенос по финансам — затраты на открытие/закрытие, эксплуатацию, сроки и методика. Не использовать одно время движения в качестве полной стоимости.

## Завершение

Релиз достаточен, если P0 закрыты либо перечислено, какие P0/тесты не выполнены и почему. Отдельно сохранить проверенные факты, технические допущения, сценарные результаты и нерешённые вопросы. Не придумывать реальные результаты. Отчёт о новых изменениях не должен переписывать результаты данного аудита.
