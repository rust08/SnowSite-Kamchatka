# SnowSite v4.1.1 — независимый аудит вычислительного ядра

## Резюме

Продукт пригоден как сценарный компаратор одного дополнительного места, но **пока не решает обобщённую задачу размещения площадок**. Приоритет — корректность назначения объёмов и ранжирования; затем комбинации, ограничения и альтернативы, независимый API, документация. Не переписывать карту и текущий сайт.

## 1. Метод, границы и воспроизводимость

Изучены все основные исходники `src/optimizer.mjs`, `src/routing.mjs`, `src/server.mjs`, схема/данные сценария, проверки, CI, `public/lib/core.js`, релевантные части `public/app.js`, README и `docs/03_MATH_MODEL.md`, `06_LEGAL_SCREENING.md`, `08_ACCEPTANCE_TESTS.md`, `17_HANDOFF_SESSION_LOG.md`, `18_FINAL_REPORT.md`. Распакован точный пользовательский ZIP. Node 22.16.0, Python 3.13.5, SciPy 1.17.0. Выполнено `npm test`: 39/39; `npm run check`: PASS. Браузерный E2E не запускался в данном аудите (предыдущие результаты — отчёт авторов). Только локальная модель и синтетические эксперименты; полевых данных, актов и сведений о реальной ёмкости площадок нет. Правовой документ в проекте изучен как инженерный источник требований, актуальность права заново не удостоверялась. Никаких файлов конфиденциальных обращений не использовано.

Граф: 9 983 узла, 12 354 ребра, версия `pkgo-27233df581c6`, SHA-256 `0e0a464f7d92057fa5bbad634c083ad0c1923294597d989ead386b393acf7ad2`, снимок 19.11.2026 по документации. Контроль `tools/check-data.mjs` проверяет именно данный граф. Сохранить OSM-атрибуцию и источники.

## 3. Подтверждённые численные дефекты

### CRIT-01: инверсия ранжирования при частичных рейсах (P0)

Малый связный двунаправленный граф (длины 8,4,4,2,4 км), два источника 8 и 4 м³, Q=2, две базовые площадки с ёмкостью 8 и 3, два кандидата с ёмкостью 5 и 1. Полные данные — `audit/counterexamples.jsonl`, строка `rank_reversal`. `S2` обозначим C, `S3` — D. Текущий алгоритм: D (144 км) лучше C (148 км). Независимый полный перебор целочисленного распределения объёмов: C = 132 км, D = 144 км. Оба варианта обслуживают все 12 м³. Проблема существенна: изменяется решение о выборе кандидата. Причина: после построения цепочки рейсов поиск не меняет размеры грузовых порций; объединение/разбиение и перераспределение объёмов может быть выгоднее.

### CRIT-02: добавление необязательной площадки ухудшает расчёт (P0)

В строке `km` того же файла: 11 м³, Q=4, baseline 16 км; при добавлении кандидата S2 solver даёт 18 км; точный минимум с S2 — 16 км. При неизменных правилах и необязательном использовании кандидата старая аллокация остаётся допустимой, поэтому точный минимум км при одинаковом максимальном обслуженном объёме не должен расти. Не путать с ситуацией, когда дополнительная площадка обязательна, появились новые расходы/ограничения или увеличился обслуженный объём.

### CRIT-03: независимый точный расчёт на городском демо (P0)

Вход: `data/scenario.demo.json`, 228 м³, Q=10 м³, S0=150, S1=130, C1=C2=100 м³, все точки условные. Для каждой фиксированной комбинации использована та же матрица двух направлений, что у SnowSite, но независимо решена целочисленная задача объёмов и числа рейсов в SciPy/HiGHS, два последовательных этапа, `mip_rel_gap=0`. Во всех четырёх случаях solver вернул status=0 (optimal в своей числовой модели и допусках). Время и тариф не являются частью сравнения. Перебор маленьких примеров независим от MILP; обе проверки используют нынешний маршрутизатор как источник расстояний, а не проверяют полноту всего OSM.

| Активные площадки | Вывезено, м³ | v4.1.1 км / рейсы | Эталон км / рейсы |
|---|---:|---:|---:|
| S0 + S1 | 228 | 167.098 / 26 | 159.425990 / 25 |
| S0 + S1 + C1 | 228 | 108.556 / 25 | 108.556350 / 25 |
| S0 + S1 + C2 | 228 | 122.648 / 25 | 122.648320 / 25 |
| S0 + S1 + C1 + C2 | 228 | не реализовано | 92.228770 / 25 |

Эталон подтверждает C1 как лучший одиночный кандидат среди двух для данного сценария. При тех же допущениях два кандидата вместе дают более низкий пробег. Но в наборе всего два кандидата, значит для **ровно двух** новых площадок есть лишь одна комбинация: это не поиск лучших мест по всему городу. Смена метода меняет baseline и проценты — нельзя продолжать показывать старые 167.098 км как оптимум. Полные назначения/матрица — `audit/demo_exact.json`, `audit/demo_costs.json`; лог и скрипт `audit/exact_demo.py`. Значения округлять только для вывода, ранжировать по целым единицам расстояния.

## 5. Чего не хватает для поставленной задачи

- Поиск **по набору вариантов расположения**, а не только оценка вручную выбранной точки; явное различие земельной площадки и дорожного узла въезда. Без полного кадастра допускается набор логистических кандидатов, но не карта разрешённых земель.
- Планирование 2 существующих + 2 новых, произвольное количество фиксированных, отключаемых или перемещаемых объектов; группы замены нужны, чтобы не выбрать два места для одной и той же переносимой площадки.
- Выбор конфигурации из shortlist; топ-K **различных наборов площадок**, а не распределений на одном наборе. Исключение кандидатов или конфигураций с протоколом причины и сохранение остальных условий.
- Раздельное ранжирование для фиксированного числа новых объектов. Если число свободное, просто уменьшать км недостаточно: без CAPEX/фиксированных затрат все лишние площадки формально полезны либо нейтральны. Нужна таблица по числу объектов и альтернативы, а не фиктивный «идеальный» ответ.
- Независимый вход/выход, solver status, воспроизводимый fingerprint, JSON Schema, тесты без UI, устойчивость к таймауту и ограничениям.

## 6. Решение по данным и стратегии

По сообщению команды в ПК существует 2 площадки и ожидаются 2 новые. Не подтверждены координаты, ёмкости, юридические статусы и планы строительства. Чтобы реально выбрать две площадки, запрашиваем каталог проверяемых потенциальных земельных участков, точные въезды, доступные объёмы и горизонт расчёта, распределение потребности в снеговывозе, ограничения грузового движения, стоимость строительства/эксплуатации (если понадобится сравнение разного числа площадок). При отсутствии — показываем синтетическую задачу с явной маркировкой. CSV обращений не заменяют объёмы в м³. Не требуется искать все земельные данные для программной реализации ядра.

## 7. Вердикт / stop rule

Сначала получить правильный точный или честно ограниченный solver и доказуемый Top-K на небольшом наборе. Если это работает, а старый сайт не сломан, остановить эту итерацию. Нельзя тратить оставшийся лимит на UI, перенос в другой фреймворк, новую карту, модели погоды, многомашинный VRP, кадастровый парсинг или ИИ без конкретного требования. Реальная эксплуатационная пригодность остаётся отдельной задачей; не обещать доказанную оптимальность по всей территории и фактическую экономию.
