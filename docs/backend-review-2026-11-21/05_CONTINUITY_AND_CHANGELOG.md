## Один источник актуального состояния, история не теряется

Рекомендуемая структура в SnowSite, без дублирования всей текущей папки docs:

- `AGENTS.md` — короткое указание, какой индекс и handoff читать, правило сверки с кодом, тестами и git; не вставлять весь аудит в инструкции.
- `docs/STATUS.md` — *живой* снимок: актуальная версия/commit, что готово, следующий приоритет, неподтверждённые данные, тесты. Одна страница; ссылки на подробности.
- `CHANGELOG.md` — хронологический append-only для изменений поведения, API, алгоритма, данных и тестов. Не подменять результаты старой версии новыми.
- `docs/HANDOFF.md` — короткая передача текущей работы; исторические записи остаются в `docs/17_HANDOFF_SESSION_LOG.md`. Каждый новый агент читает последнее состояние + нужное ТЗ, а не все ZIP.
- `docs/ALGORITHM.md` — формулы, индексы/единицы, постановка, чем отличается solver от эвристики, причины/границы optimal и ограничения, complexity. Ссылки на файлы реализации и тесты.
- `docs/API.md` — версии, request/response, CLI, настройки сети, ошибки, пример интеграции.
- `docs/CODE_MAP.md` — назначение файлов/функций и поток данных; как локально найти конкретную часть, например objective → какие ограничения → какой тест.
- `docs/11_DECISIONS.md` — ADR: вопрос, решение, альтернативы, причина, цена решения, статус proposed/accepted/superseded.
- `docs/backend-review-2026-11-21/` — неизменяемый аудит и начальное ТЗ, результаты не считать текущими после изменений.
- `docs/benchmarks/` — данные тестов, версии, сценарии, machine info, параметры, результаты. Синтетика/конфиденциальность явно обозначены.

## Workflow следующего агента

1. Сверить repo + working tree + branch + HEAD (`git status --short`, `git rev-parse HEAD`), `git diff` и текущие docs. Не переключать ветку с чужими незакоммиченными правками. Не править старые артефакты на основе предположения.
2. Взять одну задачу S0–S4. Сначала воспроизвести существующее поведение и критерии; для новой функции тест на маленькой задаче. Использовать готовые решения, если доступны и лицензии/Windows/CI подходят. Timebox исследование; если блокер, fallback + запись решения.
3. Реализовать маленький осмысленный diff, затем тесты. Проверить `npm test`, `npm run check`, новый solver и CLI, browser smoke где применимо. Сохранить реальные команды и stdout summary, failed tests не скрывать. Не переименовывать stable API без миграции.
4. Обновить CODE_MAP/ALGORITHM/API если их контракты изменились, добавить CHANGELOG и актуальный STATUS. Зафиксировать тестовые данные/seed и версии solver.
5. В конце сессии записать HANDOFF: что изменено, что реально проверено, где остановились, точная следующая команда/файл, blockers, открытые задачи. Если лимит близко — сделать это прежде следующего изменения. Отдельный нормальный commit только после проверки, не `git add -A` без review. Не пушить закрытые материалы и необработанные обращения.
6. Новый агент начинает с этого файла и STATUS. Он не должен повторять завершённый этап из исходного промпта. Если STATUS противоречит коду, проверить и исправить STATUS с явным объяснением.

## Правила при смене алгоритма или данных

Не переписывать старые fixture результаты. Записать old/new, сценарий, hash, reason, status, solver version. Baseline сравнивать одинаковым методом для всех конфигураций, на одной матрице. Если обновился snapshot, записать новый хеш/дату/источник и rerun tests: не выдавать смену карты за улучшение solver. Если меняется единица расстояния, цель или политика ёмкости, версия математической модели должна меняться. Release manifest и graph integrity check — разные артефакты.
