# SnowSite Optimize API v1.0 (S3)

## Quick start
Canonical paths in v4.6: `apps/api/server.mjs`, `apps/cli/cli.mjs`, `packages/contracts/schemas/`, `workers/milp-python/`. Public imports `snowsite-kamchatka`, `snowsite-kamchatka/catalog`, `snowsite-kamchatka/network-file`, previous src entrypoints and HTTP schema/version are unchanged. Raw snapshot/evidence paths moved; see data/README.md.
Node 22+ and Python 3.13 with `python -m pip install -r workers/milp-python/requirements.txt` (SciPy 1.17.0, NumPy 2.3.5). `SNOW_PYTHON` may point to the Python interpreter in your local virtual environment; default `python3` on Unix, `python` on Windows. No external service or network request during a solve. The explicit legacy UI mode and `/api/compare` are Node-only and intentionally remain heuristic. The main map uses exact v1 by default since v4.9. `npm test` now includes exact tests and needs Python.

```sh
node apps/cli/cli.mjs examples/demo-v1.json > result.json
npm start
curl -H 'Content-Type: application/json' --data-binary @examples/demo-v1.json http://127.0.0.1:8793/api/v1/optimize
```
PowerShell: `curl.exe -H "Content-Type: application/json" --data-binary "@examples/demo-v1.json" http://127.0.0.1:8793/api/v1/optimize`.

Module:
```js
import {readFileSync} from 'node:fs';
import {loadNetwork} from './packages/routing/network-file.mjs';
import {optimize} from './packages/optimization/optimize.mjs';
const {network,networkMeta}=loadNetwork('data/snapshots/pkgo-27233df581c6/city-network.json','pkgo');
const request=JSON.parse(readFileSync('examples/demo-v1.json','utf8'));
const result=await optimize(network,request,{networkMeta});
console.log(result.search, result.alternatives);
```
`loadNetwork` hashes original file bytes; `optimize(network,request)` without transport meta uses `hash(network)` (canonical sorted JSON, exported from request.mjs). Only trusted transport should supply `networkMeta`, never user-controlled metadata. `networkHash` is the actual file SHA for HTTP/CLI. `GET /api/health` returns version/id/hash. HTTP includes the default pkgo snapshot and can register additional trusted snapshots; CLI accepts trusted operator `--network FILE --network-id ID`. No arbitrary paths in HTTP request.

## Request
`packages/contracts/schemas/optimize-request-v1.schema.json` describes JSON shape; runtime `packages/contracts/request.mjs` adds relational, numeric, screening and resource checks. `examples/demo-v1.json` is executable, synthetic. `scenario.mode=scenario_only`, explicit `horizon`, demands with `sourceStatus` and integer m³, available site capacity for that horizon, origin (`existing|candidate`), role (`fixed|optional|excluded`), access node, screening. Distinct geometryRef; same access node needs `sharedAccessJustification` for both entries. Mass density/payload paired in truck; if absent `mass_not_checked`. Closure IDs must exist; unknown graph version/hash → 409. `policy.objective=min_unserved_then_distance`, `screeningPolicy=exploratory|strict`, `topK`, `timeLimitMs` required.

- add: `exactNewSites` required. Existing sites stay only if `role=fixed` or `fixedSiteIds/includeSiteIds` says so. Exact count of active sites can also be set.
- relocate: `replacementGroups:[{id,siteIds,lower:1,upper:1}]` selects one of old/alternative places; lower 0 allows closure. Replacement candidates do not count as new additions. Existing that can move must be optional; never remove a fixed object without explicit policy change.
- greenfield: no existing or fixed sites, `exactActiveSites` required; baseline null.
- evaluate: only fixed/include sites; no optional enumeration.
- frontier: `newSiteCounts:[0,1,2]` independent cardinality rankings; no `exactNewSites`; top-level search/alternatives mirrors first k, `frontier` includes all. No economic best k without facility costs.
- exclusions: `excludedSiteIds:[{id,reason,sourceRef?,reviewer?,time?}]` or string IDs; `excludedConfigurations:[{siteIds:[...],reason,...}]` or arrays of IDs; full sorted active set, not partial subset. For re-solve copy original JSON and add only exclusion and `parentScenarioHash` = original result hash, preserve files of both runs. `scenarioHash` hashes entire canonical request including policy. No server-side database/history; caller stores inputs/results. Strict requires status documented, decision allowed, sourceRef/reviewedBy/reviewedAt, supplied by caller; still not legal certification. Prohibited/conflict always excluded. Fixed+excluded explicit error.

## Response
`packages/contracts/schemas/optimize-response-v1.schema.json`, `examples/demo-v1.result.json` generated by CLI. `solver.status` optimal / time_limit / infeasible refers to catalogue ranking, `search.rankingStatus` exact_top_k/provisional/incomplete/infeasible. Each solution contains its two solver stages, bounds/gaps in stage units; top-level stages are last evaluated primary configuration, not a global bound. Null means unknown/unavailable. On hard timeout the child is killed, partial proved solutions may remain; ranking cannot claim exact. `configurationsTotal=null` when enumeration incomplete. `coverage` refers to finite supplied catalogue, not the whole city. `baseline` original existing when screening permits, historical reference independent of user exclusions; `baselineStatus` separate. `deltaKm` and percent null unless both allocations proved and served volume equal. `assignments` aggregate per pair, not each truck; routeRef from/to and networkHash identify route context (geometry endpoint not implemented; use routing engine). `sameNode` flags shared road-node assumption; explicit intra-site distance is supported since v4.4 (see below). Time, distance, RUB conditional; no real economy or legal claim. `unresolvedChecks` and `screeningStatus:not_assessed`.

## Errors & resource policy
POST JSON only: 400 invalid JSON, 415 content type, 413 >1 MiB, 422 schema/domain/resource constraints, 409 network mismatch, 503 busy (one v1 request per server), 500 internal/solver failure (generic outside). Body error `{error,message? omitted,code,path}` i.e. `error` is message string. Valid mathematical infeasible or timeout → HTTP 200 typed result, not fake success. CLI stdout is one JSON object, diagnostics stderr; 0 completed (including mathematical infeasible), 1 internal, 2 input, 3 incomplete/time_limit. CLI errors `{error:{code,message,path}}`.

Caps: 50 demands, 30 sites, 1e6 total demand, 50 topK, 25k potential response assignments across requested rankings, 850k node×unique route-start memory estimate, 1000 configurations and 100k enumeration nodes per cardinality, 1–120000 ms shared solver/search deadline, objective <=1e13 mm conservative bound. Node HTTP worker memory old-generation cap 256 MiB; child one solve at a time, sparse matrix, threads capped for BLAS. Timeout is cooperative in matrix/enumeration, hard child deadline includes startup; a single Dijkstra/system scheduling can overshoot slightly; no OS-enforced Python RSS limit. HTTP client disconnect sends cancellation to worker; v4.8.1 verifies a stalled subprocess actually exits, busy requests receive 503, and a subsequent request succeeds. Legacy path is bounded but synchronous. No network deployment/auth. No Python package in legacy website required; Windows/CI configured and retained, paused by owner in v4.8.1; not formally accepted.

## v4.3 S3.1 (additive v1 extension)
Use `safeRequest(request)` from `packages/contracts/request.mjs`, or set `policy.preset: "preserve_existing"`. Add/frontier keep all existing sites fixed; replacements require relocate. Safe relocate fixes every existing site outside groups, each group contains exactly one original, and requires exactActiveSites and exactNewSites. A fixed exclusion is a conflict. Requests without preset retain v1.0 behavior. Screening decision is allowed/prohibited, review date is real Gregorian YYYY-MM-DD or UTC timestamp (seconds optional fractional part); supplied evidence strings are NOT verified by v1. `inputFingerprint` is canonical request+model hash excluding only parentScenarioHash and the two policy exclusion lists; use `exclusionRerun(parent,child)` to verify parent hash and unchanged inputs locally. HTTP is stateless and reports `lineageStatus:caller_supplied_unverified` for any parent reference. `apps/web/exact.html` accepts v1 JSON, opts into safe preset; no fallback. Legacy UI is explicitly approximate. Browser interaction not yet verified.

## S4.2 — optional physical constraints (additive v1 fields)
`scenario.sites[].maxTripsDuringHorizon`: integer 0…1e6 or null/absent (unknown). Non-null requires `tripLimitEvidence:{sourceRef,observedAt,horizon}` matching scenario horizon exactly. `siteUtilization` returns usedTrips, maxTripsDuringHorizon, tripLimitBinding. Null is NOT a time-feasibility proof. `scenario.demands[].snowType`: clean|with_reagents|unknown. `sites[].acceptedSnowTypes`: array of known types (empty means accepts neither known type), or null/absent, with `snowTypeEvidence` for non-null. Known mismatch disallows the pair; unknown remains permitted with warning (not legal acceptance). Evidence here is caller-supplied, not resolved by generic v1; adapter has stronger data boundary.

Optional `scenario.accessProfiles:{loaded:{grossKg,widthMm,blockedEdgeIds,evidence},empty:{...},edgeLimits:[{edgeId,maxGrossKg?,maxWidthMm?,evidence}]}`. All evidence objects use same shape/horizon. Loaded gross ≥ empty gross and, when payload supplied, ≥ empty gross + payload; conservative full-load profile, not actual load-specific routes. Width identical for both; only supplied limits apply, no road certificate. All blocked IDs must exist. Both directed legs are evaluated independently on respective closures. `assignments[].loadedDistanceMm` / `emptyDistanceMm` plus `roundtripMm`; `matrixHash` includes graph, profiles, closures, matrix and directional legs. Generalized unserved reason is not a proof of causality; use counterfactual re-solve to isolate effects. Older reason codes preserved for unconstrained requests. `inputFingerprint` model discriminator is now fixed-charge-mm-v1.1-constraints (compare fingerprints only within same model version). Existing schemaVersion remains 1.0, additive fields. No runtime scheduling, queues, or operational certification.

## S4.3 matrix optimization (v4.3 historical; updated below)
`matrixMetrics:{cacheHit,routeStarts,startSide?}` documents construction. Forward/reverse Dijkstra from smaller set of unique nodes, one distance tree cached per direction, no arc reconstruction for pair costs. Cache key includes trusted graph hash/version, access-profile hash, directional closure IDs, ordered source and site nodes and snow compatibility inputs; TTL 120 seconds, 8 matrices, copied on read/write. JS in-process only; HTTP creates isolated worker per request, so no cross-HTTP cache. Geometry is reconstructible separately using full forward route engine with corresponding closure sets (no HTTP geometry endpoint). Existing enumeration remains bounded. On 20×30 benchmark 5 sec only 16/378 proved; provisional, not exact Top-K. Historical v4.3 status only: unified selection and multi-network registry were added in v4.4, bounded enumeration in v4.7; see sections below.

## v4.4 S4.3a — explicit unified search (additive)
Set `policy.searchStrategy: "unified_milp"` in otherwise identical v1 request. Valid values are `enumeration` (unchanged default), `unified_milp` and, since v4.7, `bounded_enumeration`. The same `optimize`/CLI/HTTP endpoint consumes this property, no additional dependency. Example:

```sh
node apps/cli/cli.mjs --network examples/v43/network.json --network-id synthetic-v43 examples/v44/add-2-plus-2.json
```

When strategy supplied, `search.strategy` is effective algorithm; `requestedStrategy` echoes requested and `counterScope` explains counters. Enumeration retains counts of configurations; unified has `enumerated=0`, `configurationsTotal=null` (not counted), `evaluated=rank attempts` (can include final infeasibility proof), `proven=proved ranks`, `coverage=finite_catalogue` (MILP models all supplied eligible sites, not a progress percentage). `solver.limits.maxRankAttempts` instead of enumeration cap; same size and time caps, total objective budget checked for full matrix. `solverStages` may include third `configurationTie` with a negative integer tie value, not km or money. All `transportDistanceMm` stage values/bounds still in mm. `solver.stages` is last rank attempt (see `stageScope`), not necessarily the best found result. Use individual `solution.solverStages` for best candidate. `provisional` may include proved prefix plus an incumbent; `search.proven` tells prefix length. `incomplete` can have no result if hard timeout occurs before worker response. No automatic fallback on timeout; explicit selection fallback only for JSON-escaped ID order incompatibility, with `selection_tie_fallback` warning and effective strategy reported. Keep strategy unchanged for exclusion rerun fingerprints. Existing requests omitting property retain previous responses/ordering. Schema stage arrays now allow 3. Previously the 5s unified run did not certify Top-K; see immutable v44/v45 logs and the separate v4.7 strategy below.

## v4.4 S4.3b — trusted multi-network HTTP registry
The server always registers the bundled pinned city for legacy endpoints. To register additional local graph snapshots, an operator starts the server with `SNOW_NETWORK_REGISTRY` pointing to a trusted JSON file conforming to `packages/contracts/schemas/network-registry-v1.schema.json`. Example (Linux/macOS):

```sh
SNOW_NETWORK_REGISTRY=examples/v44/registry.json npm start
curl http://127.0.0.1:8793/api/v1/networks
curl -H 'Content-Type: application/json' --data-binary @examples/v44/add-2-plus-2.json http://127.0.0.1:8793/api/v1/optimize
```

PowerShell: `$env:SNOW_NETWORK_REGISTRY='examples/v44/registry.json'; npm start`. JS: `startServer(0,{registryFile:'/operator/path/registry.json'})`. Each entry is `{id,version,sha256,file}` (raw file SHA-256, not canonical JSON hash). Paths resolve relative to config file or absolute; only operator startup can load them. At most 7 additions, config ≤64 KiB, each extra file ≤32 MiB, total extra raw bytes ≤64 MiB; graph validator retains existing bounds. Startup fails on missing files, duplicate ID/version, invalid graph, wrong version/hash. No automatic reload or remote retrieval. Restart to update registered snapshots; different versions of same ID allowed.

`GET /api/v1/networks` returns `{schemaVersion:"1.0",networks:[{networkId,networkVersion,networkHash}]}`; no local paths. `POST /api/v1/optimize` requires exact matching three identifiers; missing/invalid fields 422, unregistered/mismatched snapshot 409, no user-request path or URL dereferencing (extra unknown JSON fields do not select files). Worker sees only resolved snapshot. `/api/health`, `/api/network`, `/api/demo`, `/api/compare` remain pinned city-only. One concurrent exact request per server, localhost binding unchanged. Cache still in-process, not shared across HTTP workers. Registry is operator-local configuration, not an upload or public-service API. No auth or network deployment claim.

## v4.4 A08a — explicit internal per-trip distance (additive)
`scenario.sites[].intraSiteRoundtripMm`: integer 0…1e9 (roundtrip internal distance in mm) or null (unknown). Absent means legacy road-only model; explicit null omitted from cost and marks unknown. Non-null including zero requires `intraSiteDistanceEvidence:{basis:"roundtrip",valueMm,sourceRef,observedAt,horizon,networkHash,truckHash,accessProfileHash}`. `valueMm` must equal field; `networkHash` equals trusted snapshot's hash; `truckHash=hash(scenario.truck)` and `accessProfileHash=hash(scenario.accessProfiles??null)` from canonical JS `hash` (`packages/contracts/request.mjs`); horizon and date validated. Unknown value may not carry distance evidence. Generic v1 still trusts caller-supplied evidence, not official verification. Catalogue strict adapter now requires explicit basis and scoped distance/profile claims for positive values, see SITE_CATALOG. No reinterpretation of ambiguous old positive records.

For new field, `assignments[].intraSiteRoundtripMm` echoes integer or null and `roundtripMm=loadedDistanceMm+emptyDistanceMm+(intraSiteRoundtripMm??0)`; `loadedDistanceMm`, `emptyDistanceMm` remain road-only. `routeRef` identifies road endpoints only; no geometry of internal travel. Transport distance includes R_j once per trip. `sameNode` remains road-node flag. `estimatedDriveMinutes` and cost remain uniform scenario moving estimates. If some sites lack known R_j in an extended request, `intra_site_distance_unknown` warns; not an observed zero or actual economy. Fingerprints use `fixed-charge-mm-v1.2-intrasite` for new-field requests only, and old requests keep original model discriminator and matrix hash. Example:

```sh
node apps/cli/cli.mjs --network examples/v44/intrasite-network.json --network-id intrasite-v44 examples/v44/intrasite.json
```

Both search strategies support the term; no polygon or internal-route geometry engine in this release.

### v4.5 timeout durability
The private worker protocol supports intermediate phase checkpoints (not public HTTP events). On the hard deadline a previously completed phase may now yield a verified incumbent instead of null. Existing v1 response schema, `time_limit`, `provisional`/`incomplete`, and phase bounds semantics are unchanged; a checkpoint never certifies a rank. Abort and internal solver errors are not successful results.

Optional SiteRecord geometry and geometryEvidenceRef are catalogue-adapter inputs (`packages/contracts/schemas/site-record-v1.schema.json`), not new optimize policy fields. The adapter emits provenance geometryHash/reference/metadata_only, no geometry-driven routing. See SITE_CATALOG for the bounded topology and scoped evidence contract.

## v4.7: exact catalogue bounds (opt-in)

Set `policy.searchStrategy: "bounded_enumeration"`; same JSON schema version 1.0, same objective and stable configuration ID ordering. This is an additive enum value; consumers with old closed-enum schemas should update their schema before requesting it. Existing callers/defaults are unchanged.

`search.counterScope="configurations"`: `enumerated` counts admissible sets found, `evaluated` counts actual MILP solves, `proven` counts completed two-stage solves, optional `prunedByBound` counts distinct remaining sets proved unable to beat the current K-th exactly solved configuration. If `rankingStatus=exact_top_k`, complete catalogue coverage is required and `proven=evaluated`, `evaluated+prunedByBound=configurationsTotal`. Bounds are not counted as MILP solves. No exact claim on incomplete enumeration (1000 sets / 100000 nodes) or timeout. `solver.stages` still describes last evaluated set, not a global dual bound.

Example: `node apps/cli/cli.mjs examples/v47/demo-bounded.json`. On frozen seed719 `20×30`, 378 admissible sets, K=5, `bounded_enumeration` obtained `exact_top_k` in all three measured runs (1.79–2.06 s, 16 exact solves/362 pruned). See `docs/benchmarks/v47/bounded-normalized/report.json`. Not a general time or scalability guarantee; still finite-catalogue and model-only. Full service and tie conditions are verified, no change in physical assumptions, no change to exclusion fingerprint definition. Input fingerprints include strategy as before; do not change strategy on an exclusion-only rerun.

Contract verification: install dev-only `tools/contract-requirements.txt`, run `npm run test:contracts` (six schema definitions + example/negative/live CLI cases, no remote schema references). Cross-field or mathematical correctness is still checked by runtime domain validator and independent checker, not JSON Schema alone.

## v4.10.1 — legacy boundary and map import

`POST /api/compare` and direct `compareSites(network,scenario)` share `validateLegacy`. Unsupported known advanced inputs fail with HTTP 422 / `DomainError` (`code: unsupported_model`, `path` identifies the field), not a partial result or automatic fallback. The exact v1 endpoint is unchanged. The legacy shape is still the scenario-only baseline + each single candidate. Non-null v1 envelope/policy (including flattened selection overrides and editor `mapSettings`), access/constraint profiles, site selection/screening/access/internal-distance inputs and scoped constraint evidence are not applied by legacy. Any non-null cap, including 0, any non-null acceptedSnowTypes, including [], and known demand snowType are rejected. Absent/null advanced fields and unknown demand snow type are unasserted; ordinary descriptive metadata (name, provenance, legalStatus as untrusted text, assumptionDate) does not configure the heuristic. Use v1 for advanced constraints; no supported advanced field is silently ignored. Legacy root networkVersion mismatch remains 409.

The map JSON importer checks root and nested `meta.networkVersion` / `meta.networkHash` individually against the active snapshot, rejecting explicit mismatch or conflicting claims atomically before editor state changes. A supplied hash requires trusted active health hash; older documents with no or partial binding are marked as such and nodes checked on the active graph. The map export binds to the current graph, with source-binding status separate from the current export. This is not historical evidence verification. The shared browser-safe `truckCapacity` and `TRUCK_LIMITS` are used by both the importer and form; integer body/payload/density bounds 1..1000000, speed 0.1..200, rate 0..10000000, payload and density both supplied or both empty, at least 1 m³ capacity. IDs are nonblank strings <=200, preserved, not shortened. Map-only positive demands and distinct site nodes remain editor scope; the full exact API supports its broader documented domain.
