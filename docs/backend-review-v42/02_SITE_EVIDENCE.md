## 2. Три вместо двух? Рабочие гипотезы
- Интервью (2 действующие +2 будущие) — неподтверждённое состояние/план на момент беседы, scope неизвестен.
- 17.11.2026 — официальное сообщение «три вместо одной», без адресов: наиболее свежий датированный публичный счёт, не факт эксплуатационной доступности по каждой площадке.
- Исторические источники указывают на Тундровую и район Восточного/Халактырского. Не доказывают, что это конкретные три в ноябре 2026. Не соединять автоматически 2017, 2018, 2023 и 2026. Отмена старого перечня из пользовательского PDF требует первичного акта.
- Пока не подтверждены факты, честный сценарий 2+2 или 3+1 называется условным и не имеет метки «городская база». Можно подготовить оба шаблона, но не выдумывать координаты и ёмкости реальных площадок.

## 3. Запросить один раз (не блокировать программирование)
У САД/УДХТИБ, владельцев: по каждому объекту stable ID, адрес/кадастровый номер, полигон/границы, въезд/выезд с геометрией, статус и период, оператор/правовое основание, тип принимаемого снега (реагенты, загрязнения), доступный объём на конкретный горизонт, уже занятый объём, размер/время рабочего окна, пропускная способность в м³/ч или рейсах/ч, число постов выгрузки, технологическое время/очередь, ограничения по типу грузовика, подтверждённые рейсы, исходные объёмы снега по зонам и операции. Спросить, где именно три площадки сезона 2026/27; какие из них постоянные/временные, частные/муниципальные, какие принимают снег от конкретных подрядчиков. Уточнить, обсуждается ли четвёртая и есть ли список кандидатов. Для §34 и земли запросить подтверждение применимости на дату и конкретный тип снега, не утверждать, что 2017 площадку можно восстановить.

## 4. Как использовать сейчас
Исторический каталог — отличный shortlist поиска, а не истинный operating registry. После геокодирования поставить `geometryStatus=approximate`, потом проверка фактического въезда; при наличии ёмкости и согласованного типа снега сформировать отдельную exploratory модель. Пройти end-to-end `evidence -> candidate -> screened site -> request -> optimization -> ranked solutions -> exclusion + rerun`. Строгая модель без проверенного основания должна отказать; exploratory — явно условный результат с needs_review, без автоматического выбора исключённого или конфликтного объекта.

Альтернативы K — не единственная «идеальная» площадка; ранжировать полный набор по обслуженному объёму и затем пробегу, сохранять ties, допускаемое множество и метку точности. Кандидаты, не попавшие в каталог, не исследованы. Если городу нужны четыре площадки, сравнить ровно 4 действующих; если нужно решить сколько строить, добавить расходы формирования площадок отдельно. Не переносить жалобы 2025/26 в м³ и не считать среднее количество техники ёмкостью площадки.
