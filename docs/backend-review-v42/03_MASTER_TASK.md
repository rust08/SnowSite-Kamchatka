# Главное задание Codex: SnowSite v4.2 → v4.3 (backend-first)

Прочитай 00_START_HERE, аудит, реестр источников, актуальный статус и код. Не делай S0–S3 заново. Работай в новой ветке от актуального проекта. Основная цель: **независимое ядро для поиска конфигураций, а не красивый интерфейс или ещё один проект**. Быстро показать результат на проверяемых данных; если реальных данных нет, отделить синтетические сценарии от исторических сведений. Не менять «Север». Не публиковать закрытые материалы. Не переименовывать существующие документы без необходимости. Каждая итерация завершается тестами, changelog и handoff.

## P0. Контроль исходного состояния (S3.1)
1. `git status`, `git log -5`, `npm run check`, `npm test`, CLI demo, версия Node/Python/SciPy; сохранить логи. Сверить результаты с 54/54 и эталонами; при изменении кода показать разницу. Не переписывать граф. Выполнить `tests/reproduce-v42.mjs` из пакета, скопировав в tests/. Для известных проблем добавить настоящие тесты, не подгонять ожидаемое к ошибке.
2. Сохранить v1 compatibility. Ввести безопасный construction/preset для add: существующие активные площадки fixed по умолчанию. Любой перенос/закрытие — явно через режим и replacement group. В режимах relocate/add требовать однозначную cardinality для сопоставимых конфигураций. Явное исключение fixed = понятный конфликт, не молчаливое снятие. Если нужен breaking schema change — v1.1/v2 и миграция, не менять смысл публичного v1 молча.
3. Runtime validation соответствует schema, включая screening decisions, даты, числа, enum, связи, no duplicates. `reviewedAt` — реальная дата/время (выбрать ISO-8601 с оговоркой), `sourceRef` разрешается к evidence records в импорте. Указать, где граница доверия к caller. Strict не подтверждает реальное право. Даты в UTC, для локальных событий явный `Asia/Kamchatka` при необходимости. Проверка негативных кейсов в HTTP/CLI/module.
4. Согласовать два алгоритма в UI: минимум — однозначно назвать legacy «приблизительный», а новый CLI/API — точный внутри модели. Добавить небольшой адаптер для существующего сайта с явным выбором exact (или простая отдельная страница/кнопка после стабилизации) с обработкой 503/таймаута/Python unavailable; не скрывать legacy fallback и не выдавать его за exact. Не менять визуальную компоновку. Если UI блокирует backend, зафиксировать deferred U1 и предоставить однозначную CLI демонстрацию.

## P0. Каталог и геопривязка (S4.1)
5. Импортировать `evidence/site_leads.json` в новый отделённый каталог, например `data/site-evidence/pkgo-history.json`; добавить исходные ссылки, даты и scope из SOURCES, отдельные evidence records, не менять демоданные. Не записывать реальные Site records в optimize request до проверки. CSV/JSON import dry-run, JSON Schema, строгая валидация, отчёт rejected/unknown/unlocated, стабильные IDs. Не брать телефон/персональные сведения из закрытых материалов. Не геокодировать весь адрес одним предположением, если подтвердить невозможно. `siteCatalogId/version/hash`; сырой документ/первичная ссылка отдельно; evidence updates append-only/versioned.
6. Отдельная модель `SiteLead`, `SiteRecord` и adapter к `scenario.sites`. Поля SiteRecord: `id`, `sourceRefs`, `validFrom/validUntil`, `operationalStatus` (unknown/historical/active/planned/closed), `geometryStatus` (unlocated/approximate/verified), координата или polygon (GeoJSON WGS84), `accessNodeId`, `accessVerification`, `capacityM3`/availableCapacityM3 + период/измерение, `snowTypes`, screening с rule/evidence/decision/scope/date. Unknown сохраняется как null; запрещено silently 0/∞. На exploratory пользователь **явно** задаёт сценарную ёмкость/профиль и явно подтверждает условный узел, маркировать input assumptions и `needs_review`; строгий режим требует документированные allow, эксплуатационный статус и проверенный доступ/ёмкость на горизонт, не только поля строк. Не изменять loose v1 semantics тайком, на уровне catalog adapter/new mode enforce. Учитывать 2019 удаление пункта 2 как историческое изменение, не как вечный запрет. Не автоматически связывать POI с H2017-05.
7. Экспортировать проверяемую shortlist/validation report. Принять 10+1 evidence records; все исходно исключены из автоматического назначения. Синтетические примеры для 2+2, 3+1, relocate, greenfield, frontier — отдельно и с ≥6 новыми кандидатами (не только C1+C2). Возврат Top-K ≥3 при наличии альтернатив; при нехватке — причина. Exclude one site or full set; сохранять baseline отдельно, input fingerprints; проверять, что неизменны сеть, спрос, truck, costs, horizon, model and non-exclusion constraints, а новые ссылки на evidence объяснены. Сравнивать цели только при одинаковом обслуженном объёме.

## P1. Пропускная способность и маршрутизация (S4.2)
8. Сначала отдельный маленький контракт для `maxTripsDuringHorizon` (integer или null с provenance/horizon), независимый checker. Ограничение Σ_i n_ij ≤ T_j на выбранной площадке, независимо от имеющейся ёмкости. При неизвестном значении предупреждение, строгий operational режим требует заполнения только если заявляет временную реализуемость. Показать разницу между остатком по объёму и по приёмной способности, не выдавать эвристическую причинность за доказательство; можно сообщать binding constraints/контрфактуальный re-solve. Не прибавлять вымышленные очереди. При наличии параметров serviceTime, openMinutes, posts — сценарный upper bound, а не расписание. В дальнейшем можно подключить расписание из «Севера» и реальные queue logs. Сохраняй objective min_unserved_then_distance как базовый; отдельный objective time только после явного контракта и тестов.
9. Раздельные loaded/empty access profiles. Переиспользовать существующий граф и `routing.mjs` или проверенный аналог из «Севера»; два отдельно измеренных пути и ограничения рёбер, профиль зависит от массы/ширины, при unknown нельзя утверждать legal truck route. Не придумывать паспорта дорог. При консервативном full-load профиле явно отмечать, что неполный груз может иметь другие маршруты. Сценарные closed/blocked edge IDs валидировать; односторонность не ломать. Хранить hash матрицы/профилей и проверять возврат. SameNode flagged; для operational candidate требуется подтверждённый въезд и внутриплощадочное расстояние/доказанное нулевое значение. Для синтетики нулевые пути допустимы с предупреждением; не удалять существующие тесты.
10. Snow acceptance type compatibility (clean/with_reagents/unknown) — только при реальных/явно заданных данных. Ограничивать пары с подтверждённой несовместимостью, при unknown объяснить отсутствие подтверждения. Не классифицировать снег автоматически. Применимость СанПиН меняется по дате и типу снега; GIS exclusions с источником, датой и версией, неизвестное остаётся неизвестным. Правовой checker — проверка предоставленных свидетельств, не выдача разрешения.

## P1. Производительность и подключаемость (S4.3)
11. Benchmark 20 demands×30 sites и 2+2, отдельный benchmark малого графа и города, pin input/seed/hash, wall time, memory estimate, evaluated/proven/total, topK status. Не повышать жёсткие лимиты без замеров. Сначала избавить матрицу от построения всех path arcs, затем forward/reverse Dijkstra на меньшем наборе start, кеш ключ (graphHash, direction, accessProfileHash, closuresHash), лимит cache и invalidation. Тест parity старой матрицы. Лениво реконструировать пути для отображаемых назначений. Никаких сетевых запросов на solve.
12. Если перебор не укладывается в бюджет/даёт неприемлемое покрытие, использовать готовый SciPy/HiGHS (уже зависимость) unified MILP с z_j или OR-Tools после сравнительного теста и проверки лицензии/окружения. Начать с малых задач и независимого oracle. Не переписывать solver только ради названия алгоритма. При Top-K исключай точный набор (no-good inequality), не все его подмножества. Лекс стадии, фиксированные основания, группы замены, ёмкость, профили, совместимость, ограничения cardinality, tie-break. Возвращай `exact_top_k` только если каждое нужное место ранга доказано (и tie handling корректен); иначе provisional/incomplete. Учитывай limit и hard timeout, не прогонять сотни отдельных Python процессов. Сохранить текущий алгоритм как контрольный путь.
13. HTTP v1 совместим; новый контракт инструмента описать в schemas/OpenAPI или кратком typed API, CLI и JS. Никакого произвольного пути/URL в HTTP (trusted operator registry). Отдельный пример другого графа, без pkgo ID по умолчанию в расчёте. Не поднимать доступный снаружи сервер с реальными материалами без auth. Сохранение сценария и результатов caller-side; CLI output JSON, logs stderr; error taxonomy и статусы ясно документировать.

## Stop rule

Если не хватает времени — завершить P0, записать конкретный следующий шаг и команды, не притворяться, что P1 готов. Не расширять тему на SnowSignal, камеры, весь диспетчерский «Север». Не делать большой UI, не строить CAD кадастр и не обучать ML. Реальная калибровка WAIT_DATA. Сохраняй старую историю; не пушить в чужой репозиторий без согласования. Подготовить рабочий ZIP/commit и актуальные MD, результаты тестов, что осталось, фактически проверенные данные; при невозможности выполнить тест явно указать причину. Отдельно зафиксировать data licensing и source provenance.
