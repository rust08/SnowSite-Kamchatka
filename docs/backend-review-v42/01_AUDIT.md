## 3. Найденные проблемы и риски — с классификацией

### V42-01 P0: два различных алгоритма под одним интерфейсом
`public/app.js:177–182` вызывает `/api/compare`, `src/server.mjs` использует `compareSites` из старого `src/optimizer.mjs`. CLI и POST `/api/v1/optimize` используют новый MILP. Это сознательная совместимость (описана в документации), не скрытая ошибка расчёта. Но для демонстрации нельзя показывать старый рейтинг как точный. Минимально: версия алгоритма, предупреждение и явный режим exact; legacy сохраняется, но не является основной рекомендацией. Не тратить время на полный редизайн.

### V42-02 P0: add сохраняет старые площадки только при явно fixed
`src/core/request.mjs` формирует fixed из ролей и include/fixed IDs, `src/core/optimize.mjs` перечисляет optional. Это документированная семантика API, но опасная для предметной задачи. Repro: mode=add, old=existing/optional, +1 new: возвращаются `['new','old']` и `['new']` с 2 км, 0 остатка. Нельзя молча потерять существующую площадку в пользовательском режиме «добавить». Сделать безопасный preset на уровне нового запроса/адаптера; для v1 обратную совместимость явно согласовать. Перенос — только через явную группу/политику. Валидация и независимый checker должны проверять сохранение всех фиксированных объектов. В relocation помимо замены явно ограничивать новые additions (exactNewSites, exactActiveSites), иначе возможно сравнение конфигураций разной мощности.

### V42-03 P0: связка реальной геометрии и маршрута отсутствует
`src/core/request.mjs` проверяет наличие узла и координаты, не связывает точку с въездом; `src/core/matrix.mjs` использует nodeId; `src/core/allocate.mjs` выводит `sameNode`. Repro: кандидат в узле спроса получает 0 км и выигрывает кандидат с 2 км. Это математически верно для заданных входов, но для реального полигона невалидно без проверки геометрии и внутреннего подъезда. Не запрещать все sameNode в учебном режиме; в рабочем каталоге требуется отдельное доказательство подъезда, включая расстояние от площадки до сети и проезд на территории. Совпадение узла не означает физическое совпадение объектов. Не присваивать ближайший узел автоматически. Не игнорировать площадку с неизвестной ёмкостью.

### V42-04 P0: контракт screening слабее заявленной строгости
`src/core/request.mjs` принимает `reviewedAt='not-a-date'` и произвольный `screening.decision='banana'` в exploratory (repro); schema enum decision запрещает banana. Для даты JSON Schema тоже допускает просто строку. Это подтверждённое несоответствие wire schema/runtime (decision) и слабый контроль происхождения. Даже strict проверяет только caller-supplied поля, а не законность. Исправить enum, формат даты и валидацию ссылки на запись evidence; запреты/конфликты по действующему scope; версия, предмет проверки, время действия. Историческое разрешение не равно текущему. Не превращать generic `screeningStatus:not_assessed` в «разрешено». Строгий режим фильтрует документированный статус входа, но не верифицирует подписи/земельные права самостоятельно.

### V42-05 P1: пропускная способность не равна ёмкости
`solver/worker.py` ограничивает объём на площадке, но не число рейсов за окно, не время погрузки/разгрузки, не очередь. `estimatedDriveMinutes` — только движение. В реальных сообщениях январь 2026 есть очереди, недостаточная скорость расталкивания снега. Добавить отдельный optional `maxTripsDuringHorizon` с происхождением и строго согласованным периодом; ограничение Σ_i n_ij ≤ T_j; аналогично метрика fleet-hours при наличии данных, но не выдавать лимит рейсов за реальное расписание. Для первого шага не строить дискретно-событийную симуляцию. Доказательство эффекта — малый контрпример, где ближайший пункт проигрывает из-за лимита приёма. `null` = неизвестно и предупреждение, а не 0 или бесконечность без маркировки. Дефицит по времени отдельно от общей ёмкости.

### V42-06 P1: маршрутное ядро не различает гружёный и порожний доступ
`src/routing.mjs` учитывает `oneway`, `routable`, закрытия, но не ограничения массы, ширины, уклона и поворотов; исходный граф не содержит большинства паспортных параметров. В `src/core/optimize.mjs` это заявлено в assumptions. Заимствовать код/концепции из «Севера» только после сверки версии и лицензий. Два профиля рёбер (loaded/empty) по предоставленным параметрам, отдельное расстояние, границы применения. Для минимального прототипа консервативный гружёный профиль при максимальной массе; описать, что может исключить путь для частичного груза. Не подставлять произвольные ограничения. Достоверный полный маршрут для самосвала не заявлять до проверки.

### V42-07 P1: масштабирование поиска — не реально закрытый S4
Ограничения: 50 demands, 30 sites, 1k конфигураций на cardinality, 100k узлов перебора, 120s, 850k node×route-start, объём до 1e6. При 10 *новых* кандидатах выбор двух даёт 45 конфигураций; при 28 новых — 378; при 30 и выборе 4 — 27405, больше cap. Результат честно provisional/incomplete, но обход зависит от порядка идентификаторов; рейтинг усечённого множества не «лучшие по городу». Не увеличивать лимиты вслепую. Сначала benchmark 20×30, 2+2 из каталога ≥6 кандидатов, затем forward/reverse Dijkstra для меньшего множества start, матрица из distances без реконструкции путей для всех пар, кеш с networkHash/profile/closure hash. При недостаточной скорости — unified facility MILP x,n,u,z с x и n увязаны с z, вместимость умножена на z; выбор k и replacement groups; запрет предыдущего полного набора (sum z_j по выбранным минус sum z_j по невыбранным ≤ |S|-1); лексикографическая оптимизация на каждом Top-K шаге. Использовать только после oracle parity. Для детерминированного ранжирования одинаковой стоимости отдельно определить tie-break и границы proof.

### V42-08 P1/P2: история и интеграция
`parentScenarioHash` проверяет форму, но не наличие родителя и неизменность сценария. API stateless — это документировано. Для CLI/интеграции сохранять вход, выход, data/solver version, decision log и hash; при исключении сравнивать неизменяемый input fingerprint (сеть, спрос, горизонт, профили, objective, ограничения, ёмкости), меняются только исключения и, если нужно, технические лимиты. Не утверждать enforced lineage, пока не реализован resolver. `exact_top_k` относится к текущему каталогу и модели; нельзя назвать первое решение юридически разрешённым. Не вычислять проценты при разных объёмах или несопоставимых параметрах. Baseline original existing — исторический reference, не допустимый после исключения; маркировать разницу.

### V42-09 P2: экономически оптимальное количество не равно минимуму километров
При нулевой цене открытия дополнительная площадка не увеличит лучший пробег (если допускается игнорировать её), поэтому «сколько строить» без CAPEX/OPEX, периода и стоимости эксплуатации не решается. Frontier k=0,1,2,3… — независимые результаты. CAPEX/OPEX позже, при реальных данных/единых единицах. Не сравнивать 2+2 с 3+1 без одинакового объёма и горизонта.

## 4. Итог
Основная точная оптимизация закончена в рамках ограниченной модели. Не переписывать. Следующий шаг — безопасные контракты, импорт проверяемого каталога и геопривязка, воспроизводимый поиск. Затем минимальное ограничение пропускной способности, профили и benchmark. Не начинать работу с персональных обращений и отдельного SnowSignal; данные жалоб не равны объёму. Реальные места, объёмы и режим приёма — WAIT_DATA; корректный расчёт сценариев возможен сейчас.
