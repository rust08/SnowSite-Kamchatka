# Отложенный этап: фактические площадки, геометрия и пространственный анализ

**ID:** A08-DATA / S5-SITES. **Статус:** `WAIT_DATA / DEFERRED_RESEARCH` (2026-11-21, решение владельца после v4.7). Ответ от администрации/заказчика в ближайшее время не ожидается; если этап будет возобновлён, вероятно, потребуется самостоятельно найти и проверить открытые источники. Это оценка доступности данных, а не подтверждение их отсутствия в природе. **Не начинать сбор автоматически в рамках текущих технических итераций.** Не блокирует дальнейшую разработку, тестирование и демонстрацию на синтетике. Ниже — подробный backlog, а не выполненное исследование и не доказательство пригодности земли.

## 1. Цель и исходное состояние

Нужен прослеживаемый каталог существующих, планируемых и потенциальных снегоприёмных площадок Петропавловска-Камчатского на сезон 2026–2027 (и последующие версии по фактическому сезону исследования). Цель — от оценки заранее заданных точек перейти к выбору конфигураций из конечного проверяемого набора участков. Предположение о двух действующих и двух планируемых объектах пока не подтверждено: проверить число, адреса, период использования, статус и назначение. Не подгонять каталог под 2+2; это один сценарий политики, не факт о городе. При двух потенциальных новых участках есть только одна комбинация выбора двух, поэтому нужен более широкий shortlist, если он действительно существует.

На v4.7:

- `data/evidence/pkgo-history.json`: 11 SiteLead (10 исторических + одна картографическая зацепка), 9 источников, 0 допущенных реальных объектов. Исторические статусы не переносятся на новый сезон. POI «Тундра» не является проверенным въездом и не должен автоматически сливаться с H2017-05.
- `packages/catalog/`: импорт JSON/CSV, версия и hash, локальная топологическая валидация GeoJSON Polygon; явный переход SiteLead → SiteRecord → site запроса. Это уже реализовано; не переписывать.
- `packages/routing/`: дорожная матрица, профили loaded/empty, граф OSM `pkgo-27233df581c6`, хеш зафиксирован в STATUS. Исторический граф не обновлять незаметно; новые версии регистрировать отдельно.
- `packages/optimization/`: ёмкости, лимит рейсов за горизонт, совместимость типов снега, явно заданный внутриплощадочный пробег, fixed/optional/excluded, exact Top-K. Результат только по входному каталогу, не по всей территории города.
- GeoJSON сейчас ограничен локальным WGS84 Polygon (не MultiPolygon; точность, лимиты и правила в SITE_CATALOG). Геометрия — метаданные; не вычисляет площадь, вместимость, пригодность, въезд автоматически. Фактический подъезд/connector и полевые измерения отсутствуют.

Для строгого допуска нужны все scoped evidence из SITE_CATALOG, а также реальная проверка их подлинности оператором.

## 4. Процесс обработки и происхождения данных

1. Реестр поиска: дата, запрос/канал, URL, состояние доступа, ответственный, найденные документы/страницы, пробелы. Разделить публичную ссылку и локальный материал, проверить лицензию до публикации.
2. Для каждого источника: stable source ID, тип, издатель, название/номер, дата публикации и действия, точная ссылка, дата просмотра, страница/пункт, извлечённое утверждение, область (site/horizon/network/truck где применимо), метод, проверяющий, статус/конфликт; хеш допустимой сохранённой копии при наличии.
3. Сформировать SiteLead с привязками к источникам и неопределённостью. Для потенциального участка отдельно хранить гипотезу, а не присваивать active. Сопоставить дубликаты по документам, геометрии и смыслу физической ёмкости; разные ID не должны удваивать одну площадку. Спорные совпадения отправлять на ручную проверку. При конфликте источников сохранить оба, не выбирать тихо.
4. Геопривязка: разделить координату приблизительного местоположения, земельный контур, полезную зону и въезд/выезд. Хранить оригинальные CRS/геометрию/точность; явная конвертация в EPSG:4326 [lon,lat], проверка точности 1e-7 и topology runtime; неподдерживаемое не округлять/упрощать молча. Для площади использовать подходящую метрическую проекцию или проверенный геодезический расчёт, не градусы². Проверить доступ к узлу на обе стороны и отдельно длину соединителя, не подменять его расстоянием до ближайшей точки.
5. Сформировать новый версионированный evidence snapshot и отдельно SiteRecord с подтверждёнными полями. Не менять прошлый `pkgo-history.json`, его источники или benchmark. Dry-run импорта через `tools/import-site-leads.mjs`; для нового ID/version использовать предусмотренный JS-интерфейс, а не default старого аудита. Сохранить отчет accepted/rejected/unknown/unlocated/ineligible. Сверить schema/runtime и hash.
6. Адаптация в оптимизатор только явным вызовом `adaptSiteRecord` с контекстом networkMeta, horizon, asOf, truck, profiles, mode, origin/role. Strict: `access_verification`, `capacity_measurement`, `screening_allow`, `operational_status`, при геометрии `site_geometry`; точные claims, сроки и ссылки как в SITE_CATALOG. Программная проверка соответствия не удостоверяет оригинал. Exploratory: явно заданные conditional assumptions, `needs_review`; documented prohibited/conflict/closed не допускаются. Планы не превращать в active ради strict.
7. Подготовить новый сценарий с отдельным входом, hash, фактами/гипотезами, сетью, датами, объёмами и профилем. Не изменять демо; rerun сравнения конфигураций при одинаковой постановке. Для реального прогноза потребуется S5: независимый подтверждённый спрос по источникам и временному горизонту, доступная техника, эксплуатационные/дорожные условия. Без них результаты сценарные. При изменении доказательств записывать exclusion reason/parent hash, хранить исходный результат.

## 5. Геометрия и будущий GIS backlog (предложение, не реализовано)

Согласовать перед новой разработкой после возобновления. Размещать чистые пространственные функции в `packages/catalog/` или отдельном `packages/gis/` после ADR (без зависимости от HTTP/UI/solver); инструменты пакетного импорта/экспорта — `tools/` или CLI; данные/версии — `data/evidence/`; синтетические fixtures — `examples/`, тесты — `tests/`. Не требовать внешнего платного API или БД для ядра. Проверить лицензии и воспроизводимость зависимостей, resource caps, негативные тесты. Порядок:

| ID | Задача | Приёмка / ограничения |
|---|---|---|
| GIS-01 | Импорт границ из согласованных форматов, метрическая обработка | На синтетике валидный Polygon проходит; неподдерживаемый CRS, невалидные/слишком большие/неподдерживаемые MultiPolygon или форматы отклоняются объяснимо; исходник/единицы/точность и все преобразования зафиксированы |
| GIS-02 | Spatial screening по предоставленным зонам | Пересечение/буфер только по явному правилу, CRS и его источнику; тесты касания, отверстий, пересечения, неполноты слоёв. Unknown → needs_review, не approved; known prohibition исключается |
| GIS-03 | Candidate generation, явно ограниченная область/каталог | Из разрешённого к исследованию слоя участков или явно условной сетки; параметры/seed/coverage фиксированы. Не называть автоматические точки разрешёнными землями. Не выдавать restricted/sampled за весь город |
| GIS-04 | Дедупликация пространственных кандидатов | Совпадения по геометрии, кадастровому ID и физическому объекту; overlap/near duplicates в отчёт, ручное решение; не складывать одну ёмкость дважды |
| GIS-05 | Сценарная оценка ёмкости | `V_est = A_useful × h_assumed × f_shape` при явно заданных площади в м², высоте в м, коэффициенте формы 0..1; свободная ёмкость отдельно с учётом уже занятого объёма. Границы, высота и коэффициент не выдумывать для фактических данных. Не выдавать оценку за измерение; анализ диапазонов, тесты единиц/нулей |
| GIS-06 | Access analysis / connectors | Въезд отдельно от графа; оценка snap distance с заданным пределом, неоднозначные случаи требуют проверки. Учитывать направленность, ограничения loaded/empty, connector и внутриплощадочный пробег без двойного счёта. Не объявлять nearest node доступным |
| GIS-07 | GeoJSON export для QGIS/интеграции | Выбранные участки и точки доступа, ID конфигурации, score, screening status, source refs/hash, scenario/network hash, coverage; без выдуманных геометрий, конфиденциальных полей и автоматического approval |

Приёмка GIS не заменяет научную, инженерную или правовую верификацию. Для новых задач без реальных слоёв допускается отдельный полностью синтетический набор, явно обозначенный `scenario_only`; не повышать статус S5.
